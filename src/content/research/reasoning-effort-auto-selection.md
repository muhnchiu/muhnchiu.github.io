# 推理档位自动选择：成本优化的主战场从「选模型」细化为「这个 prompt 需要多用力想」

> 推理模型的「想多久」是独立于「用哪个模型」的成本维度。同一个模型，高档位和低档位的思考 token 开销可能差数倍。HeyCubit/effortless 这类工具让一个小模型逐 prompt 判定档位——简单问题降档、复杂任务升档，用户不再手动扳开关。本文以它为代表，重点不在工具本身，而在它显式化的一条经济学约束：跨模型路由省下的钱，常被 prompt 缓存重建抵消。

## 00. 研究概览

### TL;DR

**研究对象**：「每 prompt 自动选择推理档位」工具模式（样本：HeyCubit/effortless，MIT 许可第三方 CLI mod）。

**为什么值得关注**：推理档位是日常使用中最大的成本变量之一。更重要的是该项目显式化了缓存经济学——活跃会话中途换模型触发的缓存重建，常常把跨模型路由省下的推理钱抵消掉（在缓存有效的活跃会话中）；同模型内调档通常没有这个惩罚（部分厂商在档位变化时也可能重建缓存，需按具体模型版本核实）。这改写了「省 token」两条路线的优先级。

**最重要的发现**：

1. 成本优化的第一性约束不是模型单价，而是缓存结构：每模型维护独立缓存，在长上下文、原模型缓存仍有效的活跃会话中换模型，通常得不偿损（缓存作废需全价重读）——effortless 因此把跨模型切换默认关闭。
2. 判定者架构已成可复制的通用模式：小模型判定（约 1 秒）+ 短跟进豁免 + 用户手动改档即关 Auto（用户永远赢）+ 额度过 80% 自动封顶。
3. 档位纪律可以完全不依赖工具手动执行，无需额外安装、引入风险较低，但仍需在实际使用中观察质量与成本变化。

**核心限制或不确定性**：效果数据（较 medium 省 21%、较 high 省 29%、较 xhigh 省 42%）全部为项目自建基准，未经独立复现；第三方 mod 存在密钥管理与供应链信任风险；判定错误的质量回归风险真实存在。

**当前决策**：**测试验证**——先按档位纪律手动实践一至两周积累基线，不急于安装工具。

**下一步**：从下一次编码会话开始执行 8.1 的手动档位纪律记录。

### 研究定义

**核心问题**：推理档位和「选哪个模型」是同一类决策吗？prompt 缓存如何改变「跨模型省钱」与「同模型调档」两条路线的相对成本？

**研究范围**：推理档位机制的由来与经济学、自动判定的架构模式、与跨模型路由的成本对比、配套上下文管理。不包含：effortless 自报数据的独立复现（未验证）、编码 CLI 产品评测、各厂商 API 定价明细（未逐一核实）。

**研究背景**：Dev Radar 2026-10-12 收录；当前 AI Coding 工作流以长会话为主，缓存保温与档位分级两个杠杆此前未被系统性利用。

## 01. 快速理解

**问题出在哪里**

推理模型普及后，「想多久」成了独立成本维度：同一个模型，把档位从 low 拨到 high，思考 token 开销可差数倍。厂商把它做成了 API 参数和手动开关，但默认值偏保守（据 effortless 文档转述，medium 是官方推荐档位）。手动档位的实际问题不是不能调，而是用户很少调——不知道当前这条 prompt 该用哪一档，于是长期停在默认值：简单问题支付高档思考成本，复杂任务反而欠推理。

**它怎么做**

effortless 用一个判定者（judge）小模型逐条读 prompt 选定档位。默认 Haiku 5.5 跑在用户自己的登录上（据其文档，价格比 Haiku 4.5 低约 75%），也可选更快的 Jev 判定模型（约 0.25 秒，不确定时回退）。围绕判定还有几条纪律：短跟进（go / ok / yes）豁免判定、沿用刚才档位；用户手动改档后 Auto 关闭（用户永远赢）；5 小时或每周额度越过 80% 进 Save 模式、档位封顶 Medium；提示框常驻条显示当前档位、判定理由、上下文占用、prompt 缓存剩余保温时间。压缩与交接由便宜模型（默认 Haiku 5.5）承担。

**关键的一条经济学**

这套设计最值钱的判断是缓存结构：prompt 缓存按模型分别维护，活跃会话中途切到另一个模型，缓存就作废、上下文要全价重读。所以同模型内调档通常没有这个惩罚（部分厂商模型在档位变化时可能重建缓存，需按具体版本核实），跨模型调档在缓存有效时却常亏——这正是 effortless 把跨模型切换列为实验特性且默认关闭的原因。

**容易被误读的地方**

- **自报省 21%~42% ≠ 实测省钱**。这些数字是项目自建基准，未经独立复现，且幅度依赖任务难度分布。
- **自动调档没有让模型变聪明**。它只是成本分配决策；判定错误时，难题会被低档处理，质量回归风险真实存在。
- **省钱不等于就该换便宜模型**。在长上下文、缓存仍有效的活跃会话中换模型，触发缓存重建，省下的推理钱通常抵不过全价重读上下文的钱。

## 02. 纵向研究：背景与演进

### 2.1 起源与背景

推理模型普及之前，成本优化主要围绕「选哪个模型」。推理模型把「想多久」拆出来之后，档位成了和模型选择并列的第二个成本维度。厂商提供了档位参数，但默认值保守、用户很少主动调，于是出现了「简单问题支付高档成本、复杂任务欠推理」的结构性错配。

### 2.2 关键演进

| 时间 | 关键事件 | 变化与重要性 |
|---|---|---|
| 推理模型普及 | 档位成为成本变量；厂商提供手动档位参数 | 决策存在但被用户忽视 |
| 2026-10 | effortless 上 GitHub Trending（2026-10-12 快照 127 星/7 天；2026-10-14 复核 185 星，MIT 许可） | 判定者架构完整落地：判定、豁免、覆盖权、限额、透明条五件套 |
| 同期 | 跨模型切换被列为实验特性且默认关闭 | 缓存经济学被显式化——本案例最有价值的知识产出 |

### 2.3 关键转折与决策逻辑

- **事实**（仓库文档一手核实，2026-10-12 抓取）：判定者架构各机制、默认模型与价格口径、自报基准数字。
- **推断**：缓存结构是成本优化第一约束（由「每模型独立缓存 + 默认关闭跨模型切换」反推）；判定者模式可复制到其他编码 CLI。
- **未知**：项目公布的判定者自测准确率（若有）与真实任务表现之间无独立验证；真实节省幅度、质量回归率均无独立数据。

### 2.4 当前阶段

**第三方验证期**。概念成立（档位是真实成本变量、判定技术可行），实现轻量（CLI mod），效果证据为自报口径；叠加第三方 mod 固有风险（跟随宿主版本演进、密钥管理、供应链信任）。判断依据：单一项目、早期热度、无同类产品大规模部署证据。

## 03. 横向研究：相关方案如何分工

### 3.1 生态格局

编码 agent 的推理成本控制存在四条路线，作用于不同决策粒度，彼此不是互斥替代，而是可组合。

### 3.2 核心对比

| 维度 | 手动档位 | 跨模型分层路由 | 每 prompt 档位判定（本案） | 厂商原生自适应（方向） |
|---|---|---|---|---|
| 决策粒度 | 每会话 | 每任务/子任务 | 每 prompt | 模型内部 |
| 决策者 | 用户 | 编排层 | 小模型判定者 | 模型自身 |
| 缓存惩罚 | 无 | 高（长上下文活跃会话换模型常亏） | 通常无（同模型调档；部分厂商档位变化可能重建缓存，需按版本核实） | 无 |
| 判定成本 | 用户时间 | 编排复杂度 | 每条一次小模型调用 | 无外部判定 |
| 主要限制 | 用户不调 | 缓存经济学反噬 | 判定错误风险；效果自报 | 产品形态未确认 |

### 3.3 决定性差异

**「缓存惩罚」这一列**是四条路线的真正分界：在缓存有效的长上下文活跃会话中，跨模型路由的省钱结论通常不成立；同模型调档一般无此顾虑，但需按具体厂商缓存行为核实。这解释了为什么「每 prompt 调档」比「每 prompt 换模型」更适合自动化。

### 3.4 生态位与既有研究的边界修正

判定者模式增强编码 CLI 的成本控制层，不替代模型选择；依赖厂商开放档位参数；可能被厂商原生自适应替代（届时外部判定层价值收缩为透明度与控制权）。对本库 2026-10-06《AI 编程分层模型路由》的边界修正：任务级模型路由成立，但活跃会话内的跨模型切换受缓存经济学惩罚，纯模型路由的成本结论不能外推到 prompt 级。实际分工：任务边界清晰时用模型路由，会话连续时用档位判定。

## 04. 横纵交汇：位置、价值与未来

### 4.1 当前位置

概念验证完成、效果证据缺口期的第三方工具。机制可信（文档一手核实）、效果存疑（自报口径）。

### 4.2 核心价值

不在工具本身，而在两条知识的显式化：①档位决策可以自动化，且判定者架构已具体到可复制；②缓存结构是成本优化第一约束——即使不装任何工具，这两条都可指导日常实践。

### 4.3 关键变量

| 关键变量 | 当前情况 | 可能产生的影响 |
|---|---|---|
| 独立复现 | 无 | 决定自报数据可信度与工具采用价值 |
| 厂商原生自适应档位 | 未出现 | 出现即终结外部判定层（路径 A） |
| 缓存/档位定价结构 | 稳定 | 数量级变化将重算全部成本结论 |

### 4.4 未来可能的路径

| 发展路径 | 成立条件 | 可能结果 |
|---|---|---|
| 乐观 | 基准被独立复现 + 主流 CLI 原生集成同等能力 | 自动档位可在可信条件下使用（效果经独立验证），第三方 mod 完成使命 |
| 基准 | 自报与质疑并存，无原生集成 | 手动档位纪律为主，判定层停留小众 |
| 不利 | 判定错误致质量事故，或 mod 供应链风险兑现 | 自动判定退场，仅保留透明度工具价值 |

### 4.5 机会与风险

**主要机会**：手动档位纪律（简单问题降档、难题升档、短跟进不重设）无需额外安装工具、引入风险较低，但仍需在实践过程中观察对任务质量与 token 成本的实际影响，可立即开始积累基线。

**主要风险**：直接安装第三方 mod 意味着授权面扩大——判定模型跑在平台登录上，API key 存储路径与明文风险（项目文档自己提示了某配置路径为明文）需先核查。

### 4.6 哪些东西没有改变

- 模型能力档差没变：高档位在难题上仍必要，自动化的价值是「该高则高」而非一味压低。
- 效果证据的性质没变：21%/29%/42% 仍是自报口径。
- 第三方 mod 的信任问题没变：密钥管理与供应链审计是引入前提。

### 4.7 综合判断

这是「成本优化从选模型细化为调档位」的趋势信号，其最有价值的产出是缓存经济学约束，而非工具本身。当前正确动作是手动实践档位纪律积累基线、等待独立复现或原生集成，而非安装一个早期第三方 mod。最值得观察：独立复现结果与厂商原生自适应动向。

## 06. 工作流决策：对我有什么用

### 6.1 当前相关性

当前 AI Coding 工作流以长会话为主（缓存保温是直接优化点），API 模型栈经聚合平台接入多厂商模型（跨模型路由决策需要缓存经济学约束）。

### 6.2 能解决与不能解决的问题

| 能解决 | 不能解决 / 主要限制 |
|---|---|
| 长会话场景的档位成本优化（纪律手动即可执行） | 无法验证工具自报效果（需独立复现） |
| 多模型协作任务的切换时机决策（任务边界切换） | 不解决模型能力档差本身——难题仍需高档位 |

### 6.3 引入成本

手动纪律无需安装工具、引入风险较低（仅需改变使用习惯）；若引入工具：判定模型跑在平台登录上（授权面扩大）、密钥存储需安全核查、随宿主 CLI 版本演进的维护成本。API 订阅无新增。

### 6.4 当前采用建议

**决策：测试验证**（手动档位纪律先行一至两周；工具本身暂不安装）

**主要原因**：机制可信但效果自报；手动纪律无需安装工具、引入风险较低，且能产出引入决策所需的基线数据，同时仍需观察对质量的实际影响。

**适用条件**：所有长会话编码工作流。

**重新评估条件**：基准被独立复现，或所用编码 CLI 原生提供自动档位能力（届时升级「立即采用」并核查密钥存储方式）。
