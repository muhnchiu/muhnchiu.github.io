# 编码 Agent 代码膨胀度量基准：Parsimony 把「多写了多少代码」变成可计算指标

> 两个 AI 编码 Agent 都修好了同一个 Bug，一个只改了几十行，另一个却重写了一大段逻辑。它们在传统编码基准里可能得到相同的通过结果，但留下的代码显然不一样。Parsimony 想回答的，就是这种差异能不能被量化。

## 00. 研究概览

### TL;DR

**一句话定义**

[Parsimony](https://github.com/La5u/Parsimony) 是一个开源的编码 Agent 代码规模分析工具，采用 MIT 许可证。它分析公开基准中的代码补丁（patch），将代码拆成 AST 层面的 coding units，统计新增和删除的代码结构，并生成排行榜。分析过程不需要重新运行基准测试。

**为什么值得关注**

如今比较编码模型，最容易看到的数字还是任务通过率，也就是 solve rate。

这个指标当然重要。模型连问题都解决不了，讨论它写了多少代码也没有太大意义。但当两个模型都能完成任务时，我们还会关心另一个问题：它们为了完成任务，究竟改动了多少东西？

一个只需要修改几处判断的 Bug，如果 Agent 顺手重构了多个模块，后续维护和代码审查的负担可能会增加。当然，也不能反过来说，代码改得越少就一定越好。

Parsimony 的价值，就是让这部分差异有了一个可以观察的数字。

**最重要的发现**

1. **它不重新跑测试。** Parsimony 复用 SWE-bench Verified、SWE-bench Live、DeepSWE 等公开基准的补丁和测试结果，通过静态分析计算代码规模变化。数据和计算方法公开，具备离线复算条件。
2. **代码规模和任务成功率并不是简单的反向关系。** 官方报告，在包含至少 26 个模型的排行榜中，代码写得更多与解决更多任务呈正相关，Spearman 相关系数约为 0.33–0.60。这是相关性，不代表多写代码会提高成功率。
3. **它更适合辅助分析，而不是直接决定代码质量。** coding units 可以反映代码结构的数量变化，却无法直接评价可读性、架构合理性、安全性和长期维护成本。

**目前还不确定的地方**

Parsimony 目前没有充分证明净增 coding units 与真实维护成本之间存在稳定关系。不同任务、语言、Agent 配置也会影响结果。

此外，项目仍处于早期发展阶段。2026 年 10 月 14 日的原始研究记录显示仓库有 7 stars、Show HN 讨论获得 36 分。这些只是当时的热度快照，不应直接用来衡量方法成熟度。

**当前决策：测试验证**

暂时不把 Parsimony 当作代码质量门槛，也不因为某个模型的净增代码更多就降低对它的评价。

更实际的做法是：下次比较编码模型时，除了记录任务成功率，也记录补丁规模和改动幅度，看看它们能否提供额外信息。

**下一步**

在下一轮 OpenRouter 免费通道模型对比中，增加 added、removed、net 和 churn 记录。先从相同任务、相同语言的小规模实验开始。

### 研究定义

本次研究围绕一个问题展开：

**当两个编码 Agent 都完成了任务，我们该如何判断它们是否改动了过多代码？**

研究重点是 Parsimony 的 coding units 计算方式、公开基准数据来源、指标局限，以及它能否融入现有 AI Coding 工作流。

同时会将它与此前研究过的 gap-trap、AI 代码审查工具进行比较，弄清楚这些方案分别解决什么问题。

本次不对 Claude Code、Codex、pi 等具体 Agent 做实际输出排名，也不独立复算 Parsimony 的完整排行榜。

## 01. 快速理解：Parsimony 到底在数什么？

### 代码行数为什么不够用？

假设两个模型都修好了同一个 Bug。

模型 A 修改了 20 行，模型 B 修改了 60 行。乍看之下，A 好像更简洁。

但如果 B 的修改主要是注释、格式调整，或者把原来挤在一行里的逻辑展开，单纯比较行数就容易产生误导。

Parsimony 换了一个办法：不只数文本行，而是解析代码结构。

它会关注语句、函数调用、比较、变量名称、字面量等语法元素。注释、格式、标点和名称长度不会直接增加 coding units。

这并不意味着它能理解代码设计是否合理，只是比单纯数行数多了一层语法结构信息。

### 一个官方示例

假设原来的 Python 代码使用循环求和：

```
def total(items):
    result = 0
    for item in items:
        result = result + item
    return result
```

现在将其改成：

```
def total(items):
    return sum(items)
```

按照 Parsimony README 的计算结果：

| 统计项 | Coding units |
| --- | ------------ |
| 删除  | 13           |
| 新增  | 3            |
| 净增量 | −10          |

计算方式：

`net_units = added − deleted = 3 − 13 = −10`

负数意味着补丁使统计范围内的代码结构减少了。

这里有个细节：Parsimony 不是简单地给每一行分配一个单位。它会解析语法元素，并对修改前后的序列进行对齐，因此不能直接从代码行数推算 coding units。

### 还要看另一个指标：churn

如果只看净增量，仍然可能漏掉重要信息。

例如两个补丁：

| 指标        | 补丁 A | 补丁 B |
| --------- | ---- | ---- |
| 新增 units  | 10   | 110  |
| 删除 units  | 0    | 100  |
| net_units | +10  | +10  |
| churn     | 10   | 210  |

两者最终都净增 10 units，但 B 实际上进行了大范围替换。

因此，Parsimony 还可以用 `churn = added + deleted` 描述改动幅度。

它也提供 `structural_churn` 等诊断信息，帮助区分代码结构变化与名称、字面量等表面修改。

这几个指标放在一起，比只看一个净增数字更有解释力。

*上表为帮助理解的假设数据，不是实际模型测试结果。*

### 容易误解的三个地方

**第一，代码更少，不等于质量更好。**

有些代码看起来短，是因为省略了必要的边界处理；有些代码比较长，却可能更容易阅读和维护。

Parsimony 不会替我们判断哪种实现更合理。

**第二，它不是重新执行任务得到的性能分数。**

任务是否解决，来自已有基准的发布结果。Parsimony 本身不重新运行测试。

因此，它继承了原始基准的测试覆盖范围和结果限制。

**第三，不同语言不能直接比较。**

Python、JavaScript、TypeScript、Go 等语言的语法结构不同，分析器也不同。

官方为不同语言建立独立排行榜，不能拿 Python 的 100 units 和 TypeScript 的 100 units 直接比较。

## 02. 纵向研究：为什么现在需要这个指标？

### 2.1 从「能不能修好」到「修得怎么样」

SWE-bench 及其相关基准让编码 Agent 的能力有了比较清晰的评价方式。

给模型一个真实软件问题，让它生成补丁，再通过测试判断问题是否解决。

这种方法比只问模型编程知识题更贴近实际软件开发。

但它主要回答的是：任务有没有完成？

至于补丁修改了多少代码、是否引入不必要的结构、是否让后续维护变得复杂，通常不是 solve rate 能直接表达的。

这并不是说传统基准设计有缺陷，而是不同指标本来就回答不同的问题。

随着 AI Coding 工具越来越多地参与真实代码修改，单看任务通过率可能不足以支持完整的技术选型。

Parsimony 正是在这个背景下，尝试把代码修改规模单独拿出来观察。

### 2.2 相关思想与项目演进

代码简洁性并不是新话题。

早在 2011 年，《Code Parsimony and the Perils of Over-Abstraction》就讨论过过度抽象带来的问题。

后来，围绕 context engineering、token 效率以及奥卡姆剃刀的讨论，也不断出现类似的思考。

但这些讨论属于相关思想背景，不能据此认定它们直接促成了 Parsimony 的开发。

项目本身的关键时间节点如下：

| 时间         | 事件                         | 意义                  |
| ---------- | -------------------------- | ------------------- |
| 2024–2025  | SWE-bench 相关生态持续发展         | 积累了可供后续分析的公开补丁和评测结果 |
| 2026-09-21 | La5u/Parsimony GitHub 仓库创建 | 公开的代码规模分析工具开始形成     |
| 2026-10-13 | Parsimony 出现在 Show HN      | 获得社区关注，也引发对简洁性指标的讨论 |
| 2026-10-14 | 本次 Horizon 初次研究            | 评估其方法和工作流价值         |

### 2.3 为什么选择复用已有补丁？

Parsimony 一个比较聪明的地方，是没有重新设计一套需要模型逐个参加的编码考试。

它利用现有基准已经公布的数据，读取模型提交的 patch 和对应任务结果，再分析代码结构变化。

这样做有几个好处。

首先，不需要重新调用模型，也不需要重新执行整个任务集。

其次，研究者可以使用相同的公开数据检查计算过程。

最后，分析对象不局限于未来的新模型，已有的公开提交也可以纳入研究。

但这同样带来了限制：原始补丁不完整、缺少源文件、解析失败或者基准测试覆盖不足，都会影响最终结果。

官方方法文档会记录无法分析的 attempt，而不是把它们当成零改动。

### 2.4 目前发展到什么阶段？

从项目生态看，Parsimony 仍然比较早期。

2026 年 10 月 14 日原始研究记录的 GitHub stars 为 7，Show HN 得分为 36。这些数字说明它当时的社区关注规模不大，但不足以直接证明方法好坏。

从实现上看，项目已经不只支持 Python。

截至本次核对的 README，排行榜还覆盖 DeepSWE JavaScript、TypeScript、Go，SWE-bench Verified、Live Python，以及 SWEeper PHP。

不同排行榜采用各自的任务集合和分析器版本。

因此，更合适的判断是：

**Parsimony 已经有可使用的公开实现和数据，但它作为通用代码质量评价标准的有效性，仍需要更多独立验证。**

## 03. 横向研究：它与其他代码质量工具是什么关系？

### 3.1 它们并不完全是竞争关系

如果把 Parsimony 与 SWE-bench、gap-trap、AI 代码审查工具放在一起看，会发现它们解决的是不同阶段的问题。

| 方案        | 主要回答的问题                | 工作阶段        | 主要限制          |
| --------- | ---------------------- | ----------- | ------------- |
| Parsimony | 模型为了完成任务，增加或删除了多少代码结构？ | 生成后分析       | 不直接判断代码质量     |
| SWE-bench | Agent 能否解决给定软件问题？      | 基准评测        | 通过率不直接反映代码规模  |
| gap-trap  | 生成过程是否触发已知规则或不良模式？     | 生成阶段        | 依赖规则覆盖范围      |
| AI 代码审查   | 提交前是否存在值得修复的问题？        | Review / CI | 效果取决于规则、模型与配置 |

这里的 gap-trap 和 AI 代码审查沿用此前 Horizon 研究中的定位，具体实现能力仍应以各自项目文档为准。

这张表真正想说明的是：**Parsimony 不需要取代已有代码审查工具，它更像是增加了一个观察角度。**

### 3.2 最重要的差异

**第一，它关注的是规模，而不是直接判断好坏。**

代码审查工具通常会尝试指出具体问题，例如潜在 Bug、不安全的实现或者不符合规范的代码。

Parsimony 不做这种判断。

它告诉我们补丁的代码结构发生了多少变化，至于这些变化是否必要，还需要其他证据。

**第二，它适合做模型行为分析。**

如果让多个模型处理相同任务，再比较它们的任务成功率、净增 units 和 churn，就可能发现不同模型的修改倾向。

例如，有的模型更倾向于局部修改，有的可能更经常进行较大范围的重写。

但这些差异也可能来自 Agent 配置、任务集合和推理参数，不能全部归因于模型本身。

**第三，它的低运行成本来自复用已有数据。**

这降低了补充分析的门槛，但不等于部署、下载、解析和维护完全没有成本。

### 3.3 它在生态中的位置

Parsimony 目前更适合放在评测和分析层，而不是生产代码的强制质量门槛。

它依赖公开基准的补丁和结果，也可以补充现有模型评测报告。

如果未来 SWE-bench 官方或大型模型评测平台直接加入类似的代码规模指标，Parsimony 的部分价值可能被整合进更大的评测体系。

不过，这只是可能的发展方向，目前没有足够证据表明这种整合一定会发生。

## 04. 横纵交汇：这个指标究竟有多大价值？

### 4.1 真正值得关注的是什么？

Parsimony 有意思的地方，不是它证明了「代码越少越好」，而是它提醒我们：任务通过率只是评价编码 Agent 的一个维度。

两个模型都能完成任务，仍然可能表现出完全不同的代码修改习惯。

过去这类差异往往需要人工翻阅大量 diff 才能形成印象。

现在至少可以先通过统一的计算规则，观察代码结构的净增量和修改幅度，再决定哪些异常值得进一步审查。

这是一个实际而有限的进步。

### 4.2 哪些因素会决定它的未来？

我认为主要有三个。

**第一，指标是否真的有预测价值。**

这是最关键的问题。

如果未来的独立研究发现，某些代码规模指标能够稳定预测维护成本、缺陷率或者审查时间，那么它们的价值就不再只是描述模型行为。

但在没有这些证据之前，不能把 net units 直接称为技术债指标。

**第二，分析范围和可比性是否足够可靠。**

官方已经支持多个语言和基准，但不同语言之间仍不能直接比较。

此外，样本覆盖、解析失败、任务难度和分析器版本，都可能影响结果。

**第三，主流评测体系是否愿意采用。**

如果更多评测平台把代码规模列为辅助指标，用户就能更容易地把任务成功率和代码修改规模放在一起看。

但即使这种做法普及，也不意味着低膨胀应该成为唯一优化目标。

### 4.3 未来可能出现的三种情况

| 发展方向       | 需要满足的条件             | 可能结果           |
| ---------- | ------------------- | -------------- |
| 成为常见辅助指标   | 计算方法稳定、数据可复现、主流评测采用 | 模型报告增加代码规模维度   |
| 继续作为独立分析工具 | 社区有需求，但缺乏统一评价标准     | 主要服务研究者和高级开发者  |
| 影响力有限      | 指标与实际质量或维护成本关联不足    | 仍可描述规模，但难以支持选型 |

这三种情况不是互斥的，也不代表概率预测。

### 4.4 哪些东西没有改变？

不管 Parsimony 的排行榜做得多完善，有几件事不会因此改变。

**代码少，不等于代码好。**

一个模型可能用很少的代码通过测试，却遗漏未覆盖的边界条件。

另一个模型可能新增更多验证逻辑，让补丁变长，但这些代码恰恰是必要的。

**通过测试，也不代表修改完全正确。**

Parsimony 复用的是原始基准结果。如果测试没有覆盖某些行为，代码规模分析也不会自动发现问题。

**代码维护仍然需要理解上下文。**

是否引入了不合理的依赖、是否破坏原有设计、是否增加了团队理解成本，这些都不能只靠 coding units 判断。

另外，Parsimony 目前不提供完整的调用图、运行时行为、可维护性或行为等价性分析。

### 4.5 综合判断

Parsimony 值得关注，因为它用相对直接的方法，把编码 Agent 的代码修改规模变成了可以比较的数据。

它没有重新发明一套复杂的基准，而是利用已经公开的补丁，让研究者多看一个过去容易被忽略的维度。

但目前还不能据此认定哪个模型的代码质量更好。

更稳妥的用法，是把它与任务成功率、实际 diff 审查和其他质量指标放在一起分析。

## 05. 证据与验证：哪些结论站得住？

### 5.1 核心结论复核

| 核心主张                                             | 类型      | 核查结果           | 依据与限制                       |
| ------------------------------------------------ | ------- | -------------- | --------------------------- |
| Parsimony 不重新执行基准测试，复用公开补丁和结果                    | 事实      | 已证实            | 官方 README 与方法文档             |
| 官方示例删除 13 units、新增 3 units，净增 −10                | 事实      | 已证实            | README 示例；本次未独立运行分析器        |
| 官方报告代码规模与 solve rate 的 Spearman 相关系数约为 0.33–0.60 | 事实      | 官方声明已确认        | 尚未独立复算，不能解释为因果关系            |
| Agent 配置会影响统计结果                                  | 事实与推断   | 有依据，但影响程度未独立量化 | 官方说明不同排行榜使用的 Agent 配置并不完全相同 |
| 净增 units 不等于代码质量                                 | 事实与方法限制 | 有充分依据          | 官方明确说明不度量可读性和设计质量           |
| 目前更适合作为辅助指标                                      | 推断      | 有条件成立          | 基于指标范围、证据缺口及当前工作流需求         |

需要强调的是，**确认官方文档写了什么，不等于已经独立验证官方的所有统计结果。**

本次核对了 README 和方法文档，但没有下载完整基准数据重新计算排行榜，也没有独立复现相关系数。

### 5.2 目前最重要的证据缺口

真正缺少的不是更多模型排名，而是回答下面这个问题：

**代码净增量较小，是否真的意味着未来维护成本更低？**

目前没有在本次研究中找到足够的独立证据，可以直接支持这一结论。

此外，还有几个需要留意的统计问题：

- 只比较成功任务，可能受到任务难度和样本构成影响。
- 部分补丁无法解析，实际参与统计的样本可能少于全部 attempt。
- 不同 Agent 配置会影响输出风格。
- 净增量可能掩盖大范围重写，需要同时观察 churn。
- 官方方法文档还记录了近似对齐、语言分析器差异和任务集合控制等限制。

这些问题不会让 Parsimony 失去研究价值，但会限制排行榜可以支持多强的结论。

### 5.3 最小验证实验

**目标**

判断在自己的 AI Coding 工作流中，代码规模指标能否为模型对比提供有用的补充信息。

**实验设计**

选择一组相同语言、相同起始代码、难度不同的真实修复任务。

让不同模型在尽量一致的 Agent 配置、工具权限和任务要求下完成任务。

记录：

| 指标                    | 用途             |
| --------------------- | -------------- |
| 任务成功 / 失败             | 判断是否完成需求       |
| Added / Removed lines | 记录基础 diff 规模   |
| Net units             | 记录代码结构净增量      |
| Churn                 | 记录总体结构改动幅度     |
| 模型与推理配置               | 识别可能的混杂因素      |
| 人工审查结果                | 判断是否存在明显不必要的改动 |

只有使用相同分析口径时，才直接比较 AST 单元数量。

如果暂时不安装 Parsimony，也可以先记录 Git diff 行数，但必须把行数与 coding units 分开，不得混用。

**成功标准**

这次实验不是为了证明代码越少越好，而是看规模指标能否稳定帮助识别值得人工复查的异常补丁。

如果多次出现「规模异常，但人工审查并未发现实际问题」，就需要重新考虑它的使用价值。

## 06. 工作流决策：对现有 AI Coding 有什么用？

### 6.1 为什么值得放进现有评测流程？

目前使用 OpenRouter 免费通道进行模型尝试时，最容易记录的是模型是否完成任务、响应速度以及调用成本。

但编码 Agent 的输出还有一个很直观的差异：有的模型修改比较克制，有的模型容易扩展修改范围。

这种感觉如果只停留在个人印象里，很难长期比较。

Parsimony 提供了一个可以借鉴的方法：把修改规模记录下来，与任务成功率放在一起看。

这不要求立即替换现有工具链。

### 6.2 它能解决什么，不能解决什么？

| 可以提供帮助           | 不能直接解决           |
| ---------------- | ---------------- |
| 观察模型的代码修改规模      | 判断某个补丁是否设计合理     |
| 对相同任务的模型输出增加比较维度 | 自动发现全部潜在 Bug     |
| 识别需要进一步审查的大幅改动   | 替代人工 Code Review |
| 为长期模型对比积累数据      | 直接预测真实维护成本       |

### 6.3 引入成本

如果只是查看现有排行榜，基本不需要额外部署。

如果要在自己的代码库中分析补丁，则需要运行分析器、准备对应源代码和补丁，并维护必要的运行环境。

官方说明 Python 分析器要求 Python 3.12 或更新版本，且 Python 分析本身没有额外运行时依赖。

JavaScript、TypeScript、Go 等语言还需要对应的解析器和工具链。

因此，比较准确的描述是：

**复用已有公开数据时，附加评测成本较低；实际接入本地工作流仍有一定配置和维护成本。**

### 6.4 当前采用建议

**测试验证，不立即部署强制门控。**

下一轮模型比较时，可以先增加补丁规模记录。

如果数据确实能帮助识别某些模型经常出现的不必要改动，再考虑引入 AST 级分析。

但在没有充分验证之前，不建议设定类似「超过多少 units 就自动拒绝」的规则。

需要重新评估的情况包括：主流评测平台开始采用类似指标、项目分析器能力有明显提升、出现独立的质量相关性研究，或者实际团队审查流程开始持续受到代码膨胀困扰。

## 07. 行动与后续观察

### 7.1 Action Items

| 行动                               | 目的            | 优先级 |
| -------------------------------- | ------------- | --- |
| 下一轮 OpenRouter 模型对比中增加 diff 规模记录 | 建立可比较的基础数据    | 高   |
| 选择同一组任务，观察 net、churn 与人工审查结果     | 判断指标是否提供额外信息  | 高   |
| 出现明显过长补丁时，对照 Parsimony 的相关排行榜    | 辅助分析模型修改倾向    | 中   |
| 团队确有持续需求后，再评估接入 CI 的可行性          | 建立观察报告，而非自动拦截 | 低   |

### 7.2 后续值得观察的变化

**一是模型代际变化。**

Parsimony 仓库保留了部分历史 cohort，可以观察模型版本变化是否伴随代码规模变化。不过，比较时仍需控制任务集合和分析器版本。

**二是推理档位的影响。**

同一个模型在不同 reasoning effort 下，是否会产生不同的修改规模，值得进一步研究。当前还不能根据外部评分匹配信息直接得出定量结论。

**三是代码规模与真实维护成本的关系。**

如果未来出现质量较高的独立研究，能够将 net units、churn 与维护时间、缺陷率、审查成本联系起来，Parsimony 的价值判断可能需要重新调整。

**四是主流评测体系的变化。**

如果类似指标成为编码模型评测报告的常见组成部分，就值得考虑将其固定纳入个人模型对比流程。
