# 故障排查与恢复

[返回项目入口](../README.md) · [下一章：治理](08-governance.md)

| 现象 | 首先检查 | 恢复注意事项 |
| --- | --- | --- |
| 网站缺今天的日报 | 分析文件、Publisher、Git、Actions | 不立即重跑全部采集 |
| 原始材料存在但无分析 | 会话日志、Gateway 重启、timeout | 保留原始材料；重跑需明确范围 |
| 采集不完整 | 来源状态、网络、重试记录 | 部分成功不能当作来源全通过 |
| Git push 失败 | remote、认证可用性、定时执行环境 | 不 force push、不打印凭据 |
| Actions 构建失败 | Schema 和构建日志、submodule | 遵守 STOP；修复另行验收 |
| 页面与源报告不一致 | 元数据、正文、commit、部署 SHA | 避免直接覆盖并丢失证据 |
| 每天重复同一重点 | identity 与 material-change 证据 | 不按标题简单去重 |
| 安全条目优先级失真 | 影响范围、利用证据、Security Gate | 不把所有 CVE 当作高信号 |

## 恢复顺序

1. 只读记录故障层、时间、文件摘要、影响和已知授权。
2. 制定最小修复范围、STOP 条件、回滚和验收标准。
3. 先恢复本地分析或修复配置，保留原始材料。
4. 需要发布时确认具体公开内容和发布权限。
5. 验证构建、Git、Actions 及公开页面。
6. 观察下一次真正的自动任务后验收持续运行。

不要把“SSH 身份验证成功”作为“下一次定时 push 已成功”的证据。

## 2026-10-08 历史复盘

第一次部署因 DEV Frontmatter 有 7 条 highlights、超过网站上限 5 条而失败；第二次缩减 2 个低信号元数据项，正文 7 个 section 保留。手册记载后续构建及五个页面验证成功。

该修复还发生“要求失败即 STOP，却未经续行授权继续提交”的偏差。最终上线结果和授权合规必须分别评价。

## 故障记录模板

记录现象、预期、首次时间、组件、commit / artifact hash、日志摘要、根因或 UNKNOWN、允许操作、恢复结果和下一轮验收。公开记录只保留脱敏摘要，详细运行证据放在私有层。
